# 물어봐 캠퍼스 DB 모델링·인터페이스 설계 발표 대본

- 발표 자료: 물어봐 캠퍼스 DB·인터페이스 설계 (12장)
- 기준: 요구사항 정의서 v1.11, DB 모델링 v1.0, API 명세서 v1.0, MVP 프로토타입(2026-10-12 시험)
- 예상 시간: 약 6분 (장당 20~40초)
- 같은 내용이 슬라이드마다 발표자 노트에도 들어 있습니다.

---

## 1. 표지 (약 15초)

안녕하세요, 캡스톤디자인 1조입니다. 오늘은 물어봐 캠퍼스의 DB 모델링과 인터페이스, 즉 API 설계를 간단히 설명드리겠습니다. 앞부분은 데이터를 어디에 어떻게 저장하는지, 뒷부분은 앱과 관리 웹이 서버와 무엇을 주고받는지입니다. 두 설계 모두 요구사항 정의서 v1.11을 기준으로 했습니다.

## 2. 전체 구조 (약 30초)

먼저 전체 구조입니다. 학생은 Android 앱으로, 학과 조교와 관리자는 웹으로 서버에 접속합니다. 이 둘과 서버가 주고받는 약속이 오늘 뒷부분에서 설명할 인터페이스, 즉 API입니다. 서버는 받은 질문으로 자료를 검색하고 sLLM으로 답을 만드는데, 이때 데이터를 저장하는 곳이 관계형 DB와 벡터 DB입니다. 이 저장 구조가 앞부분의 DB 모델링입니다. 그리고 학생의 대화 기록이나 관심 일정 같은 개인 데이터는 서버로 보내지 않고 휴대폰에만 둡니다.

## 3. 저장 구조 (약 35초)

데이터는 성격에 따라 세 곳에 나눠 저장합니다. 첫째, 관계형 DB인 SQLite에는 수집한 문서와 청크 원문, 답변 대기 질문과 FAQ, 관리자 계정처럼 서로 이어지는 데이터를 둡니다. 둘째, 벡터 DB인 Chroma에는 청크와 FAQ를 숫자 벡터로 바꾼 임베딩을 둬서, 질문과 의미가 비슷한 문장을 빠르게 찾습니다. 원문과 상태는 관계형 DB가 기준이고, 벡터 DB는 같은 ID로 검색만 맡습니다. 셋째, 대화 기록이나 관심 일정, 설정은 학생 휴대폰에만 저장합니다. 개인 데이터를 서버에 두지 않는다는 보안 요구사항을 지키기 위해서입니다.

## 4. 테이블 13개 (약 30초)

서버 테이블은 모두 13개이고, 하는 일에 따라 네 묶음으로 나눴습니다. 파란색 데이터 수집 묶음은 학교 홈페이지 어디에서 무엇을 언제 가져왔는지를 기록합니다. 주황색 답변 대기와 FAQ 묶음은 이 앱의 핵심인 '모르는 질문이 답으로 쌓이는 순환'을 맡습니다. 남색 관리자·인증 묶음은 학과 조교의 이메일 인증 로그인과 줄임말 사전을, 회색 통계·기록 묶음은 질문 수와 응답 시간, 요약 메일 발송 기록을 남깁니다.

## 5. E-R 다이어그램 (약 30초)

E-R 다이어그램입니다. 색은 앞 장의 네 묶음과 같습니다. 관계는 모두 14개이고, 그중 13개는 1 대 N입니다. 예를 들어 원본 문서 하나는 여러 청크로 나뉘고, 중간 관리자 한 명은 여러 FAQ를 작성합니다. 가운데에 있는 답변 대기 질문과 FAQ만 1 대 0 또는 1 관계인데, 답변 대기 질문 하나에 답변은 최대 하나만 달 수 있기 때문입니다. 원본 문서의 첨부파일, 관리자가 중간 관리자를 등록하는 관계는 같은 테이블을 가리키는 자기 참조입니다.

## 6. 핵심 흐름 (약 40초)

이 앱의 핵심인 '모르는 질문이 답으로 쌓이는 과정'을 테이블로 따라가 보겠습니다. 첫째, 질문의 근거를 찾지 못하면 답변 대기 질문 테이블에 자동으로 등록되고, 알림 권한이 있는 기기라면 알림 대상 테이블에 익명 토큰이 저장됩니다. 둘째, 매일 오전 9시에 조교에게 요약 메일이 가고, 요약 메일 발송 테이블로 하루에 한 번만 보내도록 막습니다. 셋째, 조교가 답을 쓰면 승인 없이 FAQ 테이블에 저장되고 답변 대기 질문은 답변완료가 됩니다. 넷째, 답 한 건만 임베딩해서 벡터 DB에 넣기 때문에 1분 안에 반영됩니다. 다섯째, 질문했던 기기에 알림을 보낸 뒤 토큰을 지웁니다. 그다음부터 같은 질문은 이 FAQ를 근거로 바로 답합니다.

## 7. 제약 조건 (약 35초)

요구사항에 적힌 규칙 중 데이터와 관련된 것은 코드에만 맡기지 않고 DB 구조로도 지키게 했습니다. 같은 기기의 같은 질문은 한 번만 등록되도록 알림 대상 테이블에 두 컬럼을 묶은 고유 조건을 걸었고, 질문 하나에 답변이 하나만 달리도록 FAQ의 답변 대기 번호도 고유 조건입니다. 조교 이메일을 삭제하면 인증 코드와 세션이 함께 지워져 로그인이 바로 끝나지만, 그 조교가 쓴 FAQ는 남습니다. 인증 코드는 원문이 아니라 해시만 저장합니다. 그리고 학생 이름, 학번, 기기 ID, IP 같은 컬럼은 처음부터 두지 않았고, 알림용 토큰만 예외로 두되 보낸 뒤 바로 지웁니다.

## 8. API 공통 규칙 (약 30초)

이제 인터페이스입니다. 요구사항 FR-019에서 API는 JSON으로 하고 상세 명세는 설계 단계에서 정한다고 했는데, 그 명세를 만든 것입니다. API는 두 갈래입니다. 학생 앱이 쓰는 앱 API는 5개이고, 로그인 없이 쓰며 이름이나 학번을 받지 않습니다. 학과 조교와 관리자가 쓰는 관리 웹 API는 13개 묶음이고, 이메일 인증 코드로 로그인하면 12시간 동안 세션이 유지됩니다. 중간 관리자 관리나 보충 문서처럼 관리자만 쓸 수 있는 기능은 권한을 나눴습니다. 시간은 모두 한국 표준시로, 오류는 같은 형식으로 돌려줍니다.

## 9. 질문하기 API (약 35초)

앱 API에서 가장 중요한 것은 질문하기, POST /api/v1/ask 하나입니다. 앱은 질문, 캠퍼스, 고른 카테고리, 그리고 알림을 허용했다면 익명 토큰을 보냅니다. 서버는 답변 유형을 네 가지로 구분해서 돌려줍니다. 학교 자료로 답했으면 '문서', 조교가 등록한 답으로 답했으면 'FAQ', 캠퍼스 같은 조건이 빠졌으면 '되묻기', 근거가 없으면 '근거없음'이고, 이때 질문이 답변 대기에 자동 등록됩니다. 앱은 이 유형을 보고 화면을 다르게 그립니다. 답변과 함께 출처 최대 3개와 처리 시간도 돌려줍니다.

## 10. 관리 웹 API (약 30초)

관리 웹 API는 조교가 실제로 쓰는 순서대로 보시면 됩니다. 먼저 이메일을 넣으면 6자리 코드가 메일로 가고, 그 코드로 로그인합니다. 이때 등록되지 않은 이메일을 넣어도 같은 안내가 나오게 해서, 어떤 이메일이 등록돼 있는지 밖에서 알 수 없게 했습니다. 로그인하면 답변 대기 목록을 같은 질문이 많은 순으로 보고, 답변을 작성하면 앞에서 본 흐름대로 FAQ 반영과 알림까지 한 번에 처리됩니다. 중간 관리자 이메일 관리처럼 관리자만 쓰는 기능은 조교가 호출하면 거절됩니다.

## 11. MVP 구현 범위 (약 35초)

마지막으로 설계 중 지금 프로토타입에 들어간 범위입니다. 13개 테이블 중 청크, 답변 대기, FAQ, 질문 통계 4개를 먼저 만들었고, 앱 API는 질문하기와 서버 상태, FAQ 보기 3개를 구현했습니다. 설계와 다른 점도 있습니다. FAQ 임베딩은 Chroma에서 오류가 나서 지금은 SQLite에 저장해 계산하고 있고, 관리 웹은 메일 발송 계정이 정해지지 않아 임시 비밀번호로 로그인합니다. 알림은 아직 구현하지 않았습니다. 그래도 이 앱의 핵심인 근거 없음, 자동 등록, 조교 답변, FAQ 반영까지의 흐름은 시험 9개를 모두 통과했습니다.

## 12. 정리 (약 20초)

정리하겠습니다. 데이터는 관계형 DB, 벡터 DB, 휴대폰 세 곳에 나눠 두고, 서버 테이블은 13개, 관계는 14개입니다. 인터페이스는 앱 API 5개와 관리 웹 API 13개 묶음으로, 모두 JSON으로 주고받습니다. 다음 단계로는 평가 질문 80개를 만들어 검색 정확도와 모델을 비교하고, 프로토타입에 아직 없는 테이블과 API를 차례로 구현하겠습니다. 감사합니다.

## 예상 질문

| 질문 | 답변 |
|---|---|
| 왜 DB를 두 종류나 쓰나요? | 관계형 DB는 "이 답변이 어느 질문에 달렸는지"처럼 이어진 데이터를 정확히 관리하고, 벡터 DB는 "의미가 비슷한 문장"을 빠르게 찾습니다. 역할이 달라서 나눴고, 원문과 상태의 기준은 관계형 DB입니다. |
| 학생 개인정보는 정말 저장하지 않나요? | 학생 관련 테이블에 이름·학번·기기 ID·IP 컬럼이 없습니다. 질문 문장도 저장하기 전에 이름·학번·전화번호 형태를 가립니다. 알림용 익명 토큰만 예외인데, 알림을 보내거나 30일이 지나면 지웁니다. |
| 왜 SQLite인가요? | 시연은 노트북 한 대에서 돌리고 동시 사용자가 많지 않아, 설치가 필요 없는 SQLite로 충분합니다. 나중에 사용자가 늘면 PostgreSQL로 옮길 수 있게 표준 SQL 타입으로 설계했습니다. |
| 프로토타입이 설계와 다른 부분은요? | FAQ 임베딩을 SQLite에 두는 것과 임시 비밀번호 로그인입니다. 앞의 것은 Chroma 오류 우회, 뒤의 것은 메일 발송 계정이 정해지면 설계대로 바꿉니다. |
| 조교 답변을 승인 없이 바로 공개해도 되나요? | 교수님 피드백과 팀 결정으로 즉시 반영으로 정했습니다. 잘못된 답은 조교나 관리자가 수정·삭제하면 바로 다시 반영됩니다. 조교 인터뷰에서 승인 단계가 필요한지 다시 확인할 예정입니다. |
