## 1. 표지 (약 15초)

안녕하세요, 캡스톤디자인 1조입니다. 물어봐 캠퍼스의 중간 현황을 발표하겠습니다. 물어봐 캠퍼스는 학사일정, 통학버스, 공지 같은 학교 정보를 채팅으로 물으면 학교 자료를 근거로 답하는 앱입니다.

## 2. 요약 (약 35초)

먼저 결론입니다. 설계 산출물을 마쳤고, 핵심 흐름이 동작하는 MVP까지 만들었습니다. 기능 요구사항 33개 중 20개를 시작했고, 그중 7개는 구현, 13개는 일부 구현입니다. 조교 답변 흐름 시험은 9개 모두 통과했습니다. 다만 검색 정확도는 평가 질문셋이 없어 아직 재지 못했고, 파인튜닝도 시작하지 못했습니다.

## 3. 일정 (약 35초)

계획서 일정과 비교하면, 계획서, RAG 파이프라인은 완료했고 데이터 수집은 일부 완료했습니다. 앱 개발은 10주차 계획이지만 먼저 시작했습니다. 반면 7주차였던 파인튜닝이 늦어졌습니다. 프로토타입은 10월 12일에 완성했고, 데이터도 그날 수집한 자료입니다.

## 4. 설계 산출물 (약 30초)

설계 산출물은 여섯 가지입니다. 요구사항 정의서는 기능 33개이고, 화면설계서는 화면 13개, DB 모델링은 테이블 13개, API 명세서는 앱 API 5개와 관리 웹 API 13개 묶음입니다. 모델·예산 검토와 사전 설문도 마쳤습니다. 1차 설문은 9명이 모두 아산캠퍼스라 방향 참고용으로만 썼고, 2차 설문 문항은 준비했지만 아직 배포 전입니다.

## 5. 바뀐 설계 (약 45초)

교수님 피드백으로 가장 크게 바뀐 부분입니다. 처음에는 조교가 학생과 같은 사용자였는데, 답변 담당자인 중간 관리자로 바꿨습니다. 그래서 앱이 모르는 질문은 자동으로 답변 대기에 등록되고, 조교가 답하면 승인 없이 FAQ에 반영되어 같은 질문에 바로 답합니다. 학과장이나 교무처는 시스템을 직접 쓰지 않아 액터가 아니라 정보 제공 조직으로 표시했습니다. 회색으로 표시한 요약 메일과 익명 알림은 설계만 끝났고 아직 구현하지 않았습니다.

## 6. 시스템 (약 35초)

구현한 시스템입니다. 학생은 Android 앱으로, 조교는 웹으로 서버에 접속합니다. 서버는 KURE-v1으로 학교 자료를 찾고, Kanana 2.1B 모델로 근거만 사용해 답합니다. 모델은 노트북 GPU 8GB에서 돌리고 있고 아직 파인튜닝 전입니다. 학교 자료 청크 154개를 수집했고, 유료 서비스는 쓰지 않았습니다.

## 7. 동작 화면 (약 30초)

실제 화면입니다. 왼쪽은 답변과 함께 출처, 홈페이지 메뉴 위치, 원문 보기를 보여 주는 화면입니다. 가운데는 자료에 없는 질문으로, 지어내지 않고 조교에게 전달했다고 안내합니다. 오른쪽은 조교 웹으로, 그런 질문이 같은 질문 수와 함께 쌓입니다.

## 8. 진척 (약 30초)

기능 요구사항 기준으로 보면 초록색 7개가 구현, 파란색 13개가 일부 구현, 회색 13개가 미착수입니다. 일부 구현은 예를 들어 수집은 되지만 수동 실행이고, 조교 답변은 되지만 수정과 삭제가 없는 경우입니다. 미착수에는 파인튜닝과 품질 평가, 이메일 로그인, 알림이 있습니다.

## 9. 시험 결과 (약 35초)

11월 3일에 다시 시험한 결과입니다. 조교 답변 흐름 9개, 통학버스 시간 계산 10개를 모두 통과했고, 자료에 없는 질문 4개도 근거 없음으로 처리했습니다. 답변 시간은 평균 3.4초입니다. 다만 대표 질문으로 동작을 확인한 값이고, 질문 5개만 잰 시간입니다. 정확도 목표는 아직 측정하지 못했습니다.

## 10. 해결 사례 (약 45초)

시험 중 찾은 대표적인 문제입니다. 두정역에서 가장 빠른 버스를 물었는데 08시 차가 아니라 10시 15분 차를 답했습니다. 원인은 세 가지였습니다. 시간표 일부만 검색됐고, 모델이 현재 시각을 몰랐고, 표와 시각을 다 줘도 모델이 다음 차를 계산하지 못했습니다. 그래서 시간표 조회는 서버 코드가 계산하도록 바꿨고, 시험 10개를 모두 통과했습니다.

## 11. 남은 문제 (약 40초)

아직 남은 문제입니다. 가장 중요한 것은 구어체 질문입니다. 학교 동아리 뭐있냐 같은 질문은 자료가 있는데도 찾지 못했습니다. 또 지난 일정을 지났다는 안내 없이 답하고, 데이터가 10월 12일에서 갱신되지 않습니다. 요구사항과 달리 질문의 이름은 아직 가리지 않고, 30일 만료도 동작하지 않습니다. 모두 이후 작업에 포함했습니다.

## 12. 계획 (약 35초)

앞으로는 측정부터 하겠습니다. 9주차에 평가 질문 약 100개를 만들고 조교 인터뷰와 2차 설문을 진행합니다. 그 결과로 검색을 개선하고 모델을 비교한 뒤, 파인튜닝과 남은 기능을 구현합니다. 파인튜닝은 같은 질문으로 전후를 비교해 좋아졌을 때만 반영합니다. 12주차에 구현현황을 발표하겠습니다.

## 13. 위험 (약 25초)

가장 큰 위험은 일정입니다. 그래서 우선순위 상과 시연 흐름부터 구현하고, 파인튜닝이 늦어지면 현재 구조로도 시연할 수 있게 하겠습니다. 오른쪽은 앞으로 정해야 할 사항입니다. 특히 시간 조회를 코드로 처리하는 방식을 요구사항에 반영할지는 검토가 필요합니다.

## 14. 정리 (약 15초)

정리하겠습니다. 핵심 흐름은 실제 학교 자료로 동작합니다. 다음 단계는 평가 질문셋으로 정확도를 재는 것이고, 12주차까지 남은 기능을 채우겠습니다. 감사합니다.
