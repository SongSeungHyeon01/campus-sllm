# sLLM 모델 비교 (2026-11-17)

**결론: 답변 모델을 SKT A.X 4.0 Light (7B, 4bit)로 정한다.**

- 정답이 가장 많고 (62/63), 함정 질문에서 없는 정보를 지어내지 않았고, 생성 속도도 가장 빠른 축이다 (평균 2.1초).
- 라이선스는 Apache-2.0이다.

## 성능 테스트 방법

### 1. 평가 질문셋

파일: `ask-campus/eval/questions.jsonl`, 108문항.

**문항 종류**

| 종류 | 문항 수 | 의미 | 통과 기준 |
|---|---|---|---|
| answer | 80 | 자료에 답이 있는 질문 | 답변 유형이 '문서'이고, 기대 문자열(`expect`) 중 하나가 답에 들어 있다 |
| none | 20 | 자료에 답이 없는 질문 (예: "학식 메뉴 알려줘") | 답변 유형이 '근거없음'이다. 근거없음 답변은 조교 답변 대기로 넘어간다 |
| trap | 8 | 자료에 일부만 있는 질문 (예: 기말고사 기간은 있는데 장소는 없음) | 사람이 답을 읽고, 자료에 없는 정보를 지어냈는지 판단한다 |

**문항 구성**
- 분야: 학사공지 23, 학사일정 21, 일반공지 16, 장학 13, 통학버스 9, 동아리 8, 학사 7, 시설 5, 생활 3, 기타 3
- 말투: 정식 76, 구어체 32 (예: "등록금 반 돌려받을 수 있는 마지막 날 언제야")
- 캠퍼스: 아산 74, 영동 34

**문항 형식 예시**
```json
{"id": "A01", "kind": "answer", "domain": "학사일정", "style": "정식", "campus": "아산",
 "q": "2학기 기말고사 기간이 언제야?", "gold": ["제 2학기 기말고사:"],
 "expect": ["12.08", "12월 8일", "12월 08일", "12. 08"]}
```
- `gold`: 정답 근거가 들어 있는 자료 조각(청크)의 앞부분
- `expect`: 날짜·금액 표기가 여러 가지라서 허용하는 표기를 모두 적은 목록

**채점에서 빼는 문항**
- answer 80문항 중 9문항은 `expect`가 없어서 자동 채점하지 않는다. 공지가 여러 개라 정답을 하나로 정하기 어려운 문항이다. 그래서 자동 채점 대상은 71문항이다.
- 71문항 중 8문항은 sLLM까지 가지 않아 모델과 상관없이 결과가 같다.
  - 7문항은 검색 점수가 기준(`MIN_SCORE` 0.60)에 못 미쳐 '근거없음'으로 끝나고 틀린다: A32, A36, A45, A57, A58, A59, A62.
  - 1문항은 통학버스 시간표라 코드가 계산해서 맞힌다: A74.
- 그래서 모델 비교는 **sLLM이 실제로 답을 만든 63문항**으로 한다.
- 검색 성능은 따로 쟀다 (`scripts/eval_retrieval.py`): 상위 3개 안에 정답 자료가 들어온 비율이 79/80 (98.8%)이다.
  - 이 수치는 점수 기준을 적용하지 않은 것이다. 위 7문항도 대부분 정답 자료를 상위 3개 안에 찾지만, 점수가 0.60에 못 미친다. 기준값 조정이나 재순위(reranker)로 개선할 부분이다.

### 2. 실행 흐름

`scripts/model_compare.py`가 질문마다 실제 서버와 같은 `rag.ask()`를 부른다.

1. KURE로 질문을 임베딩한다. Chroma에서 상위 5개를 찾고, 점수 0.60 미만은 버린다.
2. 남은 근거가 없으면 sLLM을 부르지 않고 '근거없음'으로 끝낸다.
3. 통학버스 시간표 질문은 코드가 계산해서 답한다. sLLM을 거치지 않는다.
4. 나머지는 근거 3개를 시스템 프롬프트에 넣어 sLLM이 답을 만든다.
   - 답이 "찾을 수 없습니다" 류면 (`llm.is_not_found`) '근거없음'으로 바꾼다.
   - 빈 항목, 맺음말, HTML은 `_clean`이 지운다.

결과적으로 108문항 중 76문항에서 sLLM이 불렸다. 모든 모델이 같다.

### 3. 같은 조건으로 맞춘 것

| 항목 | 설정 |
|---|---|
| DB | 실제 DB의 복사본을 쓴다. FAQ와 답변 대기를 비워 FAQ가 먼저 답하지 않게 한다 |
| 현재 시각 | 2026-11-10(화) 14:00으로 고정한다 ('다음 버스' 같은 질문 때문) |
| 프롬프트 | `llm.py`의 SYSTEM 프롬프트를 모든 모델에 똑같이 쓴다 |
| 생성 | greedy (`do_sample=False`), `max_new_tokens=200`, `repetition_penalty=1.05`, `enable_thinking=False` (Qwen3의 추론 모드 끔) |
| 임베딩 | KURE-v1을 CPU에서 돌린다 (큰 모델도 GPU에 올라가도록) |
| 실행 | 모델마다 별도 프로세스로 하나씩 차례로 돌린다. 오프라인 모드(`HF_HUB_OFFLINE=1`)로 실행한다 |
| 환경 | RTX 5060 Laptop 8GB, torch 2.11 + CUDA 12.8, transformers 4.57.6 |
| 양자화 | bf16이 8GB에 안 들어가는 모델은 bitsandbytes로 8bit(4B급) 또는 4bit(7B)로 줄인다 |

### 4. 측정 항목

| 항목 | 재는 방법 |
|---|---|
| 정답 /63 | 위 통과 기준으로 자동 채점한다 |
| 자료에 없는 질문 거르기 /20 | none 문항 중 '근거없음'으로 끝난 수 |
| 함정 8문항 | 답변 원문을 사람이 읽고 판단한다 (자료에 없는 번호·날짜·이름을 만들어냈는지) |
| 평균 생성 시간 | `llm.answer()` 한 번의 실행 시간을 76번 재서 평균을 낸다 (검색 시간은 뺀다) |

| 라이선스 | 모델 저장소의 LICENSE 파일과 Hugging Face 표기 |

모델별 결과는 질문마다 답변 유형, 통과 여부, 응답 시간, sLLM 호출 여부, 정리 전·후 답변을 JSON으로 남긴다.

### 5. 재현

`ask-campus` 폴더에서 실행한다. 서버는 끄고 돌린다.

```
set ASK_EMBED_DEVICE=cpu
set ASK_LLM_MODEL=skt/A.X-4.0-Light
set ASK_LLM_QUANT=4bit
.venv\Scripts\python scripts\model_compare.py 결과.json --eval
```

- `--eval`을 빼면 예전 비교용 19문항으로 돈다.
- 어댑터를 시험할 때는 `ASK_LLM_ADAPTER=<Hugging Face ID>`를 추가한다.

## 해석

- **기존 Kanana 1.5**는 자료에 답이 있는데도 "찾을 수 없습니다"라고 답한 질문이 5개였다. 정답 수가 낮은 주된 이유다.
- **RAG 안전성 어댑터**를 붙여도 정답 수(57)는 늘지 않았다.
- **8bit 모델**(Qwen3-4B, Konan, KONI)은 정답 수는 괜찮다. 하지만 bitsandbytes 8bit 연산이 느려서 답 하나에 10~70초가 걸려 서비스용으로는 맞지 않는다.
- **EXAONE 계열**은 비상업용 라이선스라서, 나중에 학교 외부에 배포하면 문제가 될 수 있다.
- **Midm**은 T08("아산 생활관 신청 기간이랑 문의 전화번호")에 "7월 1~5일"이라고 답했다. 이 날짜가 자료에 있는지 확인이 필요하다.

## 확인할 것

- [x] **A.X 서버 적용 시험** (2026-11-18): KURE를 GPU에 함께 올려도 최대 6.36GB로 8GB 안에 들어간다.
  - 비교용 19문항에서 정답 12/12, 근거없음 4/4, 평균 생성 3.2초가 나왔다.
  - 서버 기본값(`config.py`)을 A.X 4bit로 바꿨고, `bitsandbytes`를 requirements.txt에 추가했다.
  - 이 노트북에서는 4bit로 개발하고 시연한다. bf16은 약 15GB라 8GB GPU에 안 들어간다.
  - 필요하면 GPU가 더 큰 다른 서버로 옮길 수 있다 (사용자 의향, 2026-11-18). 그 서버의 GPU 메모리가 16GB 이상이면 4bit 대신 bf16으로 돌려 정확도와 속도를 다시 잰다 (`ASK_LLM_QUANT`를 비운다).
- [x] **A11 정답 기준** (2026-11-18 확인): 정답 기준은 맞다. 시험 시각이 11/10이라 '다음 학기'는 2027-1학기이고, 정답은 01.06~01.12다.
  - 검색에서 2026-2학기 복학 자료 3개가 1~3위를 차지했다. 2027-1학기 자료는 4위라서 sLLM에 넘어가지 못했다 (sLLM에는 3개만 넘긴다).
  - 그래서 모델은 지난 학기 날짜로 답했다. 날짜를 기준으로 다가오는 일정을 우선하는 검색 개선이 필요하다.
- [x] **N12 분류** (2026-11-18 확인): 분류는 맞다. 자료에 계절학기 수강료는 없다.
  - 24,000원은 KCU·OCU 학점교류 과목의 '컨텐츠사용료'(1과목 3학점당)다.
  - 모델들이 이 금액을 계절학기 수강료로 잘못 옮겼다. 다른 항목의 숫자를 가져다 붙인 오답이다.
- [x] **동아리 3문항** (A57 동아리 수, A58 연합회 사무실, A59 풋살 동아리; 2026-11-18 확인): 답은 '동아리현황' 자료에 있다 (19개, 명현관 2층, P.O.S).
  - 검색도 이 자료를 1위로 찾는다. 다만 한 조각에 여러 동아리가 섞여 있어 점수가 0.52~0.58로 기준 0.60에 못 미친다.
- [ ] 요구사항정의서의 기술 스택(Kanana 1.5)을 A.X 4.0 Light로 바꾼다.

## 모델 결정 이후 답변 품질 개선 (2026-11-18)

모델은 A.X 4bit로 두고, 검색과 자료를 고쳤다.

| 단계 | 바꾼 것 | 정답 | 자료에 없는 질문 거르기 |
|---|---|---|---|
| 시작 | 기준값 0.60, 공개 페이지 자료 154건 | 63/71 | 19/20 |
| 1 | 기준값 0.55 | 68/71 | 18/20 |
| 2 | 학교 FAQ 14건 + Q&A 166건 추가 | 65/71 | 16/20 |
| 3 | 공식 자료를 먼저 넘기고 Q&A는 1건만 붙임 | 69/71 | 15/20 |
| 3 (질문셋 수정 후) | N04·N07·N13을 '답 있음'으로 옮김 | **72/74** | **15/17** |

**1. 기준값 0.55**
- 0.60, 0.55, 0.50, 0.45를 시험했다.
- 0.50 이하는 정답이 1개 더 늘었지만 맞히던 문항(A52)을 틀리고, 자료에 없는 질문을 하나 더 놓쳤다.

**2. FAQ·Q&A 추가** (`src/ingest/run_login.py`, `.env`의 학교 계정 사용)
- Q&A는 2021년 이후에 답변이 달린 글만 넣었다.
- 개인정보 처리
  - 작성자 이름은 저장하지 않고, 본문에 그 이름이 나오면 가렸다.
  - 전화번호, 학번, 이메일은 가렸다.
  - 원본 HTML은 저장하지 않았다.
- 학교 답변에 다시 붙어 있던 질문 원문('원 본 글 시 작 … 종 료')을 지웠다.
- 그런데 질문 모양이 비슷한 Q&A가 검색 1~3위를 다 차지했다. 그래서 날짜가 적힌 학사일정·공지가 sLLM에 넘어가지 못했다 (계절학기 기간 A05·A19, 조기졸업 전화번호 A25 등).

**3. 공식 자료 우선** (`rag._ranked_hits`)
- 공지, 학사일정, 통학버스, 동아리, FAQ에서 2건을 먼저 넘기고, Q&A는 1건만 붙인다.
- 프롬프트에 규칙 7을 추가했다: Q&A는 예전에 한 학생에게 한 답변이므로, 공지와 다르면 공지를 따르고 개인 사정에 대한 답은 일반 안내로 쓰지 않는다.

**4. 빈 번호 정리**
- 한맥 연락처(T02)에 답 전체가 '010--'로 나온 것을 지운다.
- 실제 번호, 시간, 날짜는 그대로 두는 것을 확인했다.

**질문셋 수정**
- N04(편입생 학점 인정), N07(졸업 학점), N13(군휴학 준비물)은 Q&A·FAQ에 답이 생겨 '자료에 없음'에서 '답 있음'으로 옮겼다. id는 그대로 두었다.
- 수정 전 파일은 따로 백업했다.

**남은 오답**
- **A11** "다음 학기 복학 신청": 다가오는 학기가 아니라 지난 학기 날짜로 답한다. 날짜 기준 정렬이 필요하다.
- **A57** "동아리 몇 개": 동아리현황 조각에 답이 있는데 근거없음으로 답한다.
- **N06** "학생증 재발급": 증명서 발급 안내를 학생증 재발급으로 잘못 답한다.
- **N10** "성적장학금 평점": 다른 장학금의 기준을 끌어온다. 숫자를 엉뚱한 항목에 붙이는 유형이다.

## 시험 과정에서 있었던 문제

- **18:53에 띄운 첫 시험 실행기가 종료되지 않고 남았다.** 그래서 두 시험이 GPU를 같이 쓰면서 한 답에 1~4분씩 걸렸다.
  - 남아 있던 실행기를 종료했다.
  - 이때 돌았던 모델(EXAONE 4.0, Qwen3-1.7B, EXAONE 3.5)은 다시 시험했다.
- **처음 4개 모델이 KURE를 불러오다 `AttributeError`로 실패했다.** 원인은 확인하지 못했다.
  - 남아 있던 실행기와 동시에 불러오던 시점이다.
  - 다시 시험할 때는 정상으로 끝났다.
