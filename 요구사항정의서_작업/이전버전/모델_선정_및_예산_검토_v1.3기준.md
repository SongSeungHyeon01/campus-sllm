# 물어봐 캠퍼스 모델 선정·개발 가능성·예산 검토

- 작성일: 2026-10-05
- 기준 문서: 요구사항 정의서 v1.3 (FR-016 임베딩, FR-017 sLLM, PER-001~004)
- 환율 가정: 1달러 = 약 1,400원 (금액은 모두 대략치)

## 1. 결론

| 항목 | 결론 |
|---|---|
| 개발 가능성 | **가능.** 2B급 공개 모델과 공개 임베딩 모델 조합이면 학부 2인 팀이 15주 안에 구현할 수 있는 규모입니다. 가장 큰 위험은 모델이 아니라 **앱 개발 일정과 파인튜닝용 질의응답 데이터 작성량**입니다. |
| 필요 예산 | **최소 0원**, 권장 **약 3~5만 원**, 여유 있게 잡아도 **10만 원 이내** |
| 문서 수정 필요 | 계획서·요구사항 정의서의 sLLM 후보 "Gemma / Phi-3-mini", 임베딩 후보 "ko-sroberta"를 아래 추천 모델로 바꾸는 것이 좋습니다. "파라미터 10억 개 이하" 목표는 "4bit 기준 메모리 4GB 이하" 기준만 남기는 것을 권합니다. |

## 2. 추천 모델 조합

| 역할 | 1순위 | 비교·대안 | 선정 이유 |
|---|---|---|---|
| 답변 생성 (sLLM) | **Kanana 1.5 2.1B Instruct** (카카오) | Qwen3.5 2B, Gemma 4 E2B | 한국어 특화, Apache 2.0 (상업 이용 가능), 2B급이라 무료 GPU에서 QLoRA 가능 |
| 온디바이스 시연 (확장) | **EXAONE 4.0 1.2B** (LG) | Qwen3.5 0.8B | 가장 작은 한국어 강세 모델. 단, 비상업 라이선스(교육 목적 허용) |
| 임베딩 | **KURE-v1** (고려대) | BAAI/bge-m3 | 한국어 검색 점수 상위, MIT 라이선스, Chroma·FAISS에 바로 사용 가능 |
| 리랭커 (고도화) | **bge-reranker-v2-m3-ko** | 없이 시작 | 상위 3개 정답률 목표(PER-003) 달성에 효과적, 기본 RAG 완성 후 추가 |
| 벡터 DB | **Chroma** | FAISS | 설치가 간단하고 메타데이터 필터(카테고리·캠퍼스) 지원 |

### 2.1 sLLM 후보 비교

| 후보 | 크기 | 라이선스 | 한국어 | 비고 |
|---|---|---|---|---|
| Kanana 1.5 2.1B Instruct | 2.1B | Apache 2.0 | 강함 | 국내 개발, 2025년 5월 공개 |
| Qwen3.5 2B | 2B | Apache 2.0 | 보통 이상 | 2026년 3월 출시, 폰 구동 목표 |
| Gemma 4 E2B | 실효 2.3B (임베딩 포함 5.1B) | Apache 2.0 | 보통 이상 | 2026년 4월 출시, 다국어·멀티모달 |
| EXAONE 4.0 1.2B | 1.2B | 비상업(NC), 교육 목적 허용 | 강함 | 온디바이스용 설계 |
| (기존 후보) Phi-3-mini | 3.8B | MIT | 약함 | 2024년 모델, 한국어 약해 제외 권장 |

### 2.2 임베딩 후보 비교 (한국어 검색 벤치마크 MTEB-ko-retrieval, nDCG@10)

| 후보 | 점수 | 비고 |
|---|---|---|
| KURE-v2 | 0.8160 | 점수 1위지만 late interaction 방식이라 Chroma·FAISS에 바로 쓰기 어려움 |
| **KURE-v1** | **0.7616** | 일반 벡터 방식, 1순위 추천 |
| BGE-m3-ko | 0.7547 | |
| BAAI/bge-m3 | 0.7509 | 다국어 기본형 |
| (기존 후보) ko-sroberta-multitask | 다른 벤치마크에서 0.53 수준 | 제외 권장 |

벤치마크 점수는 공개 자료 기준입니다. 최종 선택은 우리 테스트 질문셋(80개)으로 비교해서 정합니다.

## 3. 개발 가능성

### 3.1 사용할 수 있는 자원

| 자원 | 사양 | 용도 |
|---|---|---|
| 팀 노트북 (송승현) | RTX 5060 Laptop GPU 8GB, 메모리 31GB | 개발·시연 서버. 2B 모델 4bit(약 1.5GB) + 임베딩 모델(약 1~2GB) 동시 구동 가능 |
| Google Colab 무료 | T4 16GB, 세션 최대 12시간, 혼잡 시간 할당 거부 가능 | QLoRA 파인튜닝 |
| Kaggle Notebooks 무료 | 주당 약 30시간, T4×2 또는 P100 | Colab이 막힐 때 대체 |
| 안드로이드 폰 | 팀원 개인 폰 | 앱 시연, 온디바이스 시연 |

### 3.2 구성 요소별 판단

| 구성 요소 | 난이도 | 판단 | 위험과 대응 |
|---|---|---|---|
| 데이터 수집기 | 하 | 가능 | 학교 사이트 구조 확인 완료, 공통 모듈 일부 작성됨. 구조 변경 위험은 결과 검사로 대응 |
| 임베딩·벡터 DB | 하 | 가능 | 공개 모델을 그대로 사용, 학습 불필요 |
| RAG 답변 생성 (파인튜닝 전) | 중 | 가능 | 2B 모델 원본 + 프롬프트만으로도 1차 동작 가능. 이것을 먼저 완성하는 것이 핵심 |
| sLLM QLoRA 파인튜닝 | 중 | 가능 | 2B급은 T4 한 장으로 충분. **질의응답 데이터 300~500쌍 작성이 실제 작업량**의 대부분. 시간이 부족하면 파인튜닝 없이 RAG+프롬프트로도 시연 가능 |
| 평가 (80문항, RAGAS) | 중 | 가능 | 질문셋은 데이터 수집과 함께 미리 작성 |
| 서버 (FastAPI) | 하 | 가능 | 시연 기간에는 팀 노트북에서 구동 |
| Android 앱 (Kotlin) | 중상 | 가능하지만 **일정 위험 가장 큼** | 화면 12개 중 우선순위 상 화면(메인·설정·마감 일정)을 먼저. 운영 관리 웹은 후순위 |
| 온디바이스 구동 | 상 | 확장 시연 수준에서 가능 | 1.2B 모델 GGUF + llama.cpp/MediaPipe. 1차 범위에서 제외 유지 |

### 3.3 일정 대비 (계획서 15주 기준, 10/5 현재 4주차)

| 주차 | 계획 | 현실성 |
|---|---|---|
| 3주 | 데이터 수집·정리 | 약간 지연. 수집 코드 재개 필요 |
| 5주 | RAG 파이프라인 | 가능. 파인튜닝 없이 원본 모델로 먼저 연결 |
| 7주 | sLLM 선정·파인튜닝 | 가능. 모델 비교(Kanana vs Qwen3.5)를 이때 수행 |
| 10주 | 앱 개발·통합 | 가장 빠듯함. 앱 화면 개발은 5주차부터 병행 권장 |
| 12~15주 | 발표·전시·보고서 | 가능 |

### 3.4 확인해야 할 기술 위험

- **RTX 5060(최신 Blackwell 세대) 호환성**: PyTorch·bitsandbytes 최신 버전이 필요합니다. 로컬에서 문제가 생기면 학습은 Colab/Kaggle, 로컬은 추론만(llama.cpp, Ollama 등) 쓰면 됩니다.
- **Colab 무료 GPU 할당 거부**: 혼잡 시간에 GPU가 안 잡힐 수 있어 Kaggle을 대체로 둡니다.
- **EXAONE 라이선스**: 비상업이라 캡스톤 시연에만 쓰고, 서비스로 이어가려면 Apache 2.0 모델로 바꿔야 합니다.
