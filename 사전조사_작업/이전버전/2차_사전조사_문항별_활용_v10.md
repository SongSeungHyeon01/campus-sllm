(못 찾음) 질문은 근거 없음 응답(FR-005) 테스트와 조교 FAQ 초기 데이터로 씁니다. 나온 줄임말은 동의어 사전(FR-002)에 넣습니다. 홈페이지 커뮤니티 > Q&A 게시판(로그인 없이 약 1,120건)의 학생 질문과 함께 쓰면 질문셋을 더 빨리 채울 수 있습니다. Q&A 게시판은 글로 쓴 질문이고 Q7은 채팅 말투라 둘 다 필요합니다 |

## 섹션 3. 앱 기능과 의견

| 문항 | 알 수 있는 것 | 개발에서 쓰는 곳 |
|---|---|---|
| Q8 도움될 정보 3개 | 분야별 수요 순위 | 데이터 수집 순서. 학식·시설이 많으면 FR-026(우선순위 하)을 올릴지, 장학금·취업이 많으면 수집 소스를 추가할지 판단합니다 |
| Q9 필요한 기능 3개 | 기능별 기대 순위 | FR 우선순위를 학생 기준으로 확인합니다. 우선순위 상인데 거의 선택되지 않은 기능은 10주차 통합이 빠듯할 때 미룰 후보가 됩니다. 진행보고서의 "FR-001~019 우선순위 확인"에 근거로 씁니다 |
| Q10 기다릴 수 있는 시간 | 질문 전송부터 답변 표시까지 허용 시간 | PER-001(질문 전송부터 답변 표시까지 평균 5초)이 적당한지 확인합니다. "3초 이내"가 많으면 리랭커를 빼거나 답변을 짧게 생성하는 쪽으로 판단하고, Kanana 2.1B와 Qwen3.5 2B 비교(7주차) 때 속도 비중을 높입니다. 답변을 한 글자씩 보여주는 스트리밍은 지금 요구사항에 없으므로, 필요하면 FR-001(로딩 표시)을 고치는 요구사항 변경으로 다룹니다 |
| Q11 답을 못 찾았을 때 보여 줄 것 | 근거 없음 응답 화면에서 학생이 원하는 것 | FR-005와 SCR-001-B 안내 문구를 정합니다. 지금 설계는 첫째("찾을 수 없습니다" + 조교에게 전달했다는 안내)입니다. "관련 공지 목록"이 많으면 유사도가 기준에 조금 못 미친 공지를 목록으로 보여 주는 기능을, "직접 물어볼 곳"이 많으면 카테고리별 담당 부서 연락처 안내를 추가할지 검토합니다. "추측"이 많더라도 잘못된 정보 위험 때문에 넣지 않고 발표 때 이유를 설명합니다 |
| Q12 질문 전달·공개 동의 | 답하지 못한 내 질문이 자동으로 조교에게 가고, 답과 함께 다른 학생에게 보이는 것을 받아들이는지 | 자동 등록(FR-028)과 승인 없는 FAQ 저장(FR-029)을 확인합니다. "문장을 다듬는다면"이 많으면 SCR-006-B의 '대표 질문 다듬기'(100자 이내)를 필수 단계로 둡니다. "싫다"가 많으면 근거 없음 안내에 '조교에게 전달하지 않기' 선택을 두거나, 대표 질문만 공개하고 원래 문장은 공개하지 않는 방안을 검토합니다 |
| Q13 설치 의향 | 실제로 쓸 의향의 강도 (5점) | 1차 설문(긍정 89%)과 비교합니다. Q4(휴대폰)와 같이 보면 "실제로 설치할 수 있는 사람 중 쓰겠다는 비율"을 낼 수 있습니다 |
| Q14 걱정되는 점 + 기타 | 걱정 유형별 비율, 선택지에 없던 의견 | 1차 설문과 비교합니다. 틀린 정보 → 출처 표시·근거 없음 응답(FR-004·005)과 평가(FR-018), 최신 공지 → PER-008(3시간 이내 반영), 개인정보 → 익명 이용(2.6 보안), 느린 답 → PER-001, 용량·배터리 → 서버 구동 구조 설명 근거. '기타'에 적힌 내용은 새 기능 후보로 검토합니다(1차 설문의 "메뉴 위치 찾아주기"가 FR-022가 된 것처럼) |
